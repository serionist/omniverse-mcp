# Add a fit-plan step that asks whether a plan is the right one before its review

## Goal

Every plan gets a cold read that asks whether it is the right plan before `review-plan` hunts its defects, so the
review reads the better plan once. The next five plans here (#155 to #159) are tool-contract changes, one-way doors
under `AGENTS.md`, whose shape is cheapest to choose before the review: a new tool or a parameter on an old one, which
default, one plan or two.

When this is done:

- `.claude/skills/fit-plan/` (`SKILL.md`, `questions.md`) exists, ported from simready-forge's (its #11, from
  bechtel-mvp's) and adapted to this repo, linked into `.agents/skills/fit-plan` for Codex and listed in `AGENTS.md`;
- every plan gets its fit between its first commit and its first review round: `start-work`'s review step runs
  `review-plan`, which runs `fit-plan` first;
- the fit's improvements go to the maintainer as take, leave or later, recorded in `### Fit` at the top of the plan's
  "Plan review" section, above `review-plan`'s rounds, whose improvement ids number on from the Fit's;
- the gate's `plans` check fails a plan, started from the day this lands, whose review round has no answered Fit
  above it.

In scope: the new skill, `start-work`, `review-plan`, `docs/plans/README.md`, `AGENTS.md`, the gate's `plans` check
and its tests.
Out of scope: `plugin/`, the server and the extension; `review-code`, `finish-work`, `write-skill` and
`run-scenarios`; a fit for code (`review-code`'s improvements cover it); a second fit after a round changes the design
(the next round reads the change); editing the 25 plans already merged, which are dated records.

### review-plan

- **Step 1:** no `### Fit`: run `fit-plan`, then come back. A Fit with an improvement unanswered: ask the maintainer
  and commit the answers; never a second fit.
- **Steps 2 and 3:** the reviewer reads the Fit as part of the plan; a `left` or `later` improvement comes back only
  with a reason the fit did not have; each defect noticed on the way is judged as a finding.
- **Step 4:** the round goes below `### Fit`; its improvements are `| # | Improvement | Answer |`, ids `I<n>`
  numbered on from the Fit's and every earlier round's, as this repo's recent plans already write them.
- **The description and Done means** name the Fit. `lenses.md` stays: its `simplicity` lens overlaps "cut or
  simplify", and dropping a lens loosens the review (`REVIEW.md`, The harness).

### The gate's `plans` check (Q3)

simready-forge's `fence_opens`, `fence_closes`, `plan_review_lines`, `plan_problems` and `check_plans`, ported with
its tests and their fixtures (fit I2), with one difference: this repo has 25 plans with review rounds and no Fit, and
#150's and #151's on their branches. Plans are dated records, never edited after their merge, so the Fit rule alone
reads only a plan whose file name's date is `FIT_SINCE` or later: one early return in `plan_problems` (fit I3).

- Every `.md` in `docs/plans/` but `README.md`: a name other than `YYYY-MM-DD-<slug>.md` fails, and so does a plan
  without `## Plan review`. All 25 pass both today.
- Every plan, outside fenced blocks (read as CommonMark reads them), in the `## Plan review` section: no improvement
  id is a row id twice. None of the 25 repeats one.
- From `FIT_SINCE` on: a `### Round` needs a `### Fit` above it; once a round follows the Fit, every `| I<n> |` row of
  the Fit has an answer starting `taken`, `left` or `later` (a `\|` inside a cell is not its end).
- `FIT_SINCE` is the first day after the last plan started without a fit: 2026-11-03 unless a plan is started before
  this merges. This plan and every later one get a Fit anyway, by the skills.
- It runs in the quick lane after `skill links`, detail `<n> plans`; standard library only.

Alternatives for the plans before the fit: a list of their 27 names in `gate.py`, which only shrinks (left: a
constant does the same in one line, and no plan is renamed); add a Fit to each (no: they are records); no gate check
(no: Q3).

### Alternatives

- **Fold the fit into `review-plan`** as a lens: no. The issue asks for the same skill as simready-forge and
  bechtel-mvp, so the three repos work alike, and `review-plan` is the one entry point anyway.
- **The author's own fit:** no; the author asks `questions.md` while writing, and a cold read catches what the
  author's framing hides.
- **Optional,** as bechtel-mvp's: no (Q1).

## Compatibility

No one-way door: no tool, flag, route, setting or plugin skill changes, and nothing reaches the plugin's or the
server's users.

- **Contributors, people and agents:** `start-work` starts the branch right after the issue; every plan is fitted
  before its review. A session in flight is told: `post-checkout` and `post-merge` name the changed AI setup files.
- **Plans in flight:** #150's and #151's are approved and dated before `FIT_SINCE`; they pass as they are.
- **The harness:** this touches `AGENTS.md`, `.claude/skills/`, `.agents/skills/fit-plan`, `tools/gate.py` and
  `tests/test_gate.py`. Each change tightens (a step added, a check added); no permission widens, since the fit's
  commands (`git log`, `git show`, `gh issue view`) are allowed already. A normal review is enough.
- **`AGENTS.md`** is at its 150-line cap: `fit-plan` joins the skills line and `plans` the gate's list by rewording
  those lines, not by adding any.

## Tests

`tests/test_gate.py`, unit, CI:

- a plan from `FIT_SINCE` with a round and no Fit fails; with the Fit below the round fails; with the Fit above and
  every row answered passes; a row `open` fails once a round follows, and passes while none does;
- an answer with `\|` in it is one cell; a fenced example of a review in the plan is not read, in simready-forge's
  cases: a `~~~` fence holding a backtick one, a line starting with inline code that is not a fence, a fence never
  closed, which runs to the end;
- an improvement id twice as a row id fails, in any plan; a P row that names an I id is not a repeat;
- a plan dated before `FIT_SINCE` with rounds and no Fit passes; a misnamed file and a plan with no `## Plan review`
  fail, whatever their date;
- the repo's own `docs/plans/` passes.

No live suite: nothing here reaches Kit.

## Docs

`AGENTS.md` (the skills line, the gate's list), `docs/plans/README.md` (the Plan review section), the two skills and
the new one. No `CHANGELOG.md` line: users notice nothing.

## Risks

- **A plan started today without a fit slips past the gate:** accepted. `FIT_SINCE` is set when this merges, past
  every plan started before it; the skills fit every plan regardless.
- **The fit's model guesses at Kit's APIs:** resolved by `questions.md`, which says prior art is looked up, never
  recalled, names sources that work without Context7, and has the fit say what it could not look up.
- **A fit that changes the design adds a turn for the maintainer** before every review: accepted; that turn is the
  point, and it is cheaper than a review round on the wrong design.
